Why RC

Before any of the technical detail - why does this exist?

If you've never heard of Runtime Conditions, start here. Everything else in this guide assumes you already understand the problem it's solving.

Normal life

Alice is a developer building something. Her code needs a few ordinary things to work: somewhere to store files, somewhere to cache data, and a way to call another team's API to fetch some information. None of this is unusual - almost every piece of software needs things like this. Alice writes the code, runs it on her own laptop, sees that it all works, and ships it. As far as she's concerned, the job is done.

Why it breaks production

Here comes the problem : this was all just in Alice's head. It was never written down anywhere a machine could understand. At best, These requirements scattered across a Slack thread, an old wiki page or a comment buried in some pull request. So before it's safe to go live, Jack, a platform engineer, has to go dig through all of that, piece it together by hand, and then set each need up separately, in a different system, with a different set of steps e.g:

  • Creating storage spaceBy hand, plus writing the permissions for who's allowed to use it.
  • Spinning up a cachePlus separately opening a rule that lets this app actually reach it.
  • Wiring up the other team's APIWriting down its address, opening a rule to allow the connection, and setting up a certificate so both sides trust each other.

Three ordinary needs, each one translated by hand into its own system, in its own format, by Jack, who has to guess or go ask Alice what she actually meant. And then it all has to be done again for the next environment - once for testing, once for the production. If one step is missed, or typed slightly wrong, nobody finds out until it's already broken in front of real users.

Runtime Conditions life

Here's the same story again, but with Runtime Conditions in place. This time, before Alice ever writes a line of code, Jack's team has already written down, once, what "storage," "a cache," and "an API" actually mean, and what information is needed to ask for each one. Think of it as a shared dictionary - it doesn't set anything up itself, it just agrees on the words everyone will use.

Alice writes her code exactly like before, but this time she also writes down, using Jack's dictionary, the three things her code needs: "this needs storage," "this needs a cache," "this needs to call that API." That's it - no storage permissions, no traffic rules, no certificates. Just three plain sentences.

The moment Alice submits that, and before her code ever gets a chance to run anywhere, a check runs against it automatically, using Jack's dictionary to see if her request makes sense. If she asked for something that doesn't exist, or left out something required, it gets rejected right there, with a clear reason - instead of quietly shipping and breaking later in front of real users.

Once it's accepted, Alice is done. An automated process takes her three sentences and does the rest on its own - creates the storage, spins up the cache, opens the right connection to the other team's API - in every environment, from testing to the real thing. Alice never touches a permission, a rule, or a certificate. She wrote down what her code needs, once, and the rest happens without her.

Yes, it's different from Docker Compose

A lot of teams already write a compose.yaml to describe how their services fit together, so it's a fair question: isn't that the same thing?

Not quite. A compose.yaml describes a specific, already-decided implementation - this exact Postgres image, on this exact port, wired up this exact way. Someone reading it still has to reverse-engineer the actual intent behind it: does this really have to be Postgres, or would any relational database work? What about a dependency that has no image at all, like another team's API? You can fake it with a mock, but now whoever's reading your compose file has to guess what that mock is even standing in for.

A Runtime Conditions Profile goes the other way around. Alice never describes a specific implementation - she describes the plain intent: "this needs a cache." It's not tied to any one image, port, or vendor, which is exactly why Jack's team can decide the real implementation later, and can change it without Alice rewriting anything. And because the intent is written down cleanly in one place, you could generate a compose.yaml from a Runtime Conditions Profile for local development. Going the other way - guessing a profile out of a compose file - is a lot harder, because the intent was never written down to begin with.
